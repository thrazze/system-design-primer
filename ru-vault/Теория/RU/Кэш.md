# Кэш

<p align="center">
  <img src="../../../images/Q6z24La.png">
  <br/>
  <i><a href=http://horicky.blogspot.com/2010/10/scalable-system-design-patterns.html>Источник: Scalable system design patterns</a></i>
</p>

Кэширование сокращает время загрузки страниц и снижает нагрузку на серверы и базы данных. В этой модели диспетчер сначала проверяет, поступал ли такой запрос раньше, и пытается вернуть ранее полученный результат — чтобы не выполнять работу заново.

Базам данных обычно выгодно равномерное распределение чтений и записей по разделам. Популярные элементы перекашивают это распределение и создают узкие места. Кэш перед базой помогает поглощать неравномерную нагрузку и всплески трафика.

## Уровни кэширования

### Клиентское кэширование (client caching)

Кэш может располагаться на стороне клиента (ОС или браузер), на [[Обратный прокси|стороне сервера]] либо в отдельном слое кэша.

### Кэширование в CDN

[[Сеть доставки контента (CDN)|CDN]] — это тоже разновидность кэша.

### Кэширование на веб-сервере

[[Обратный прокси|Обратные прокси]] и кэши вроде [Varnish](https://www.varnish-cache.org/) умеют отдавать статический и динамический контент напрямую. Веб-серверы тоже могут кэшировать запросы и возвращать ответы, не обращаясь к серверам приложений.

### Кэширование в базе данных

В конфигурации по умолчанию база данных обычно уже включает какой-то уровень кэширования, настроенный под усреднённый сценарий. Подгонка этих настроек под конкретный профиль нагрузки даёт дополнительный прирост производительности.

### Кэширование на уровне приложения

Кэши в оперативной памяти — Memcached и Redis — это хранилища «ключ-значение», стоящие между приложением и хранилищем данных. Поскольку данные лежат в RAM, они отдаются значительно быстрее, чем из типичной базы, хранящей данные на диске. Но RAM гораздо меньше диска, поэтому алгоритмы [вытеснения](https://en.wikipedia.org/wiki/Cache_algorithms) вроде [LRU (least recently used)](https://en.wikipedia.org/wiki/Cache_replacement_policies#Least_recently_used_(LRU)) выбрасывают «холодные» записи и удерживают в памяти «горячие».

У Redis есть дополнительные возможности:

* Опциональное сохранение на диск (persistence)
* Встроенные структуры данных: sorted sets, списки

Кэшировать можно на нескольких уровнях, которые делятся на две категории — **запросы к базе** и **объекты**:

* Уровень строки
* Уровень запроса
* Полностью собранные сериализуемые объекты
* Полностью отрендеренный HTML

Файлового кэширования по возможности следует избегать: оно усложняет клонирование инстансов и автомасштабирование.

## Кэширование на уровне запроса к базе

При каждом обращении к базе берём хеш запроса как ключ и кладём результат в кэш. У подхода есть проблемы с инвалидацией:

* Сложный запрос трудно сопоставить с кэшированным результатом и удалить его
* Если изменилась одна ячейка таблицы, придётся удалить все кэшированные запросы, которые могли её затрагивать

## Кэширование на уровне объекта

Смотрите на данные как на объект — так же, как в коде приложения. Пусть приложение собирает набор данных из базы в экземпляр класса или структуру данных:

* Удаляйте объект из кэша, если изменились данные, на которых он построен
* Это открывает дорогу асинхронной обработке: воркеры собирают объекты, потребляя свежую кэшированную версию

Что имеет смысл кэшировать:

* Пользовательские сессии
* Полностью отрендеренные веб-страницы
* Ленты активности
* Данные графа пользователей

## Когда обновлять кэш

Объём кэша ограничен, поэтому нужно выбрать стратегию обновления, подходящую под ваш сценарий.

### Cache-aside

<p align="center">
  <img src="../../../images/ONjORqk.png">
  <br/>
  <i><a href=http://www.slideshare.net/tmatyashovsky/from-cache-to-in-memory-data-grid-introduction-to-hazelcast>Источник: From cache to in-memory data grid</a></i>
</p>

За чтение и запись в хранилище отвечает приложение. Кэш напрямую с хранилищем не взаимодействует. Приложение делает следующее:

* Ищет запись в кэше — получает промах (cache miss)
* Загружает запись из базы
* Кладёт запись в кэш
* Возвращает запись

```python
def get_user(self, user_id):
    user = cache.get("user.{0}", user_id)
    if user is None:
        user = db.query("SELECT * FROM users WHERE user_id = {0}", user_id)
        if user is not None:
            key = "user.{0}".format(user_id)
            cache.set(key, json.dumps(user))
    return user
```

[Memcached](https://memcached.org/) обычно используют именно так.

Последующие чтения уже добавленных в кэш данных выполняются быстро. Cache-aside также называют ленивой загрузкой (lazy loading): кэшируются только реально запрошенные данные, так что кэш не забивается тем, что никто не спрашивает.

#### Недостатки: cache-aside

* Каждый промах кэша стоит трёх обращений, что даёт заметную задержку.
* Данные могут устареть, если их обновили в базе. Проблема смягчается установкой TTL (time-to-live), который принудительно обновляет запись, либо переходом на write-through.
* При отказе узла его заменяет новый пустой узел — задержка временно растёт.

### Write-through

<p align="center">
  <img src="../../../images/0vBc0hN.png">
  <br/>
  <i><a href=http://www.slideshare.net/jboner/scalability-availability-stability-patterns/>Источник: Scalability, availability, stability, patterns</a></i>
</p>

Приложение использует кэш как основное хранилище: читает и пишет в него, а кэш уже сам отвечает за чтение и запись в базу:

* Приложение добавляет/обновляет запись в кэше
* Кэш синхронно записывает её в хранилище
* Возврат

Код приложения:

```python
set_user(12345, {"foo":"bar"})
```

Код кэша:

```python
def set_user(user_id, values):
    user = db.query("UPDATE Users WHERE id = {0}", user_id, values)
    cache.set(user_id, user)
```

В целом write-through — медленная операция из-за синхронной записи, зато последующие чтения только что записанных данных быстры. Пользователи, как правило, спокойнее относятся к задержке при обновлении данных, чем при чтении. Данные в кэше не устаревают.

#### Недостатки: write-through

* Когда создаётся новый узел (из-за отказа или масштабирования), он не будет содержать записей, пока те не обновятся в базе. Сочетание cache-aside и write-through сглаживает эту проблему.
* Бо́льшая часть записанных данных может так и не быть прочитана; лечится установкой TTL.

### Write-behind (write-back)

<p align="center">
  <img src="../../../images/rgSrvjG.png">
  <br/>
  <i><a href=http://www.slideshare.net/jboner/scalability-availability-stability-patterns/>Источник: Scalability, availability, stability, patterns</a></i>
</p>

При write-behind приложение делает следующее:

* Добавляет/обновляет запись в кэше
* Асинхронно записывает её в хранилище, что повышает производительность записи

#### Недостатки: write-behind

* Возможна потеря данных, если кэш упадёт до того, как его содержимое доедет до хранилища.
* Реализовать write-behind сложнее, чем cache-aside или write-through.

### Refresh-ahead

<p align="center">
  <img src="../../../images/kxtjqgE.png">
  <br/>
  <i><a href=http://www.slideshare.net/tmatyashovsky/from-cache-to-in-memory-data-grid-introduction-to-hazelcast>Источник: From cache to in-memory data grid</a></i>
</p>

Кэш можно настроить так, чтобы он автоматически обновлял недавно запрошенные записи ещё до истечения их срока жизни.

Refresh-ahead снижает задержку по сравнению с read-through — но только если кэш умеет достаточно точно предсказывать, какие элементы понадобятся дальше.

#### Недостатки: refresh-ahead

* Если предсказание неточное, производительность окажется хуже, чем вообще без refresh-ahead.

## Недостатки кэша

* Нужно поддерживать согласованность между кэшами и источником истины (например, базой) через [инвалидацию кэша](https://en.wikipedia.org/wiki/Cache_algorithms).
* Инвалидация кэша — трудная задача; момент обновления кэша сам по себе добавляет сложности.
* Требуются изменения в приложении: подключение Redis или memcached.
