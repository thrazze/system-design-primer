### Удалённый вызов процедур (RPC)

<p align="center">
  <img src="../../../images/iF4Mkb5.png">
  <br/>
  <i><a href=http://www.puncsky.com/blog/2016-02-13-crack-the-system-design-interview>Источник: Crack the system design interview</a></i>
</p>

В RPC клиент инициирует выполнение процедуры в другом адресном пространстве — обычно на удалённом сервере. Процедура вызывается так, будто это обычный локальный вызов: все детали взаимодействия с сервером скрыты от клиентской программы. Удалённые вызовы, как правило, медленнее и менее надёжны, чем локальные, поэтому имеет смысл явно отличать RPC-вызовы от локальных. Среди популярных RPC-фреймворков — [Protobuf](https://developers.google.com/protocol-buffers/), [Thrift](https://thrift.apache.org/) и [Avro](https://avro.apache.org/docs/current/).

RPC — это протокол запрос/ответ:

* **Клиентская программа** — вызывает клиентскую stub-процедуру. Параметры помещаются в стек так же, как при локальном вызове процедуры.
* **Клиентская stub-процедура** — маршалит (упаковывает) идентификатор процедуры и аргументы в сообщение-запрос.
* **Модуль связи клиента** — ОС отправляет сообщение от клиента к серверу.
* **Модуль связи сервера** — ОС передаёт входящие пакеты серверной stub-процедуре.
* **Серверная stub-процедура** — демаршалит (распаковывает) результаты, вызывает серверную процедуру, соответствующую идентификатору, и передаёт ей полученные аргументы.
* Ответ сервера повторяет те же шаги в обратном порядке.

Пример RPC-вызовов:

```
GET /someoperation?data=anId

POST /anotheroperation
{
  "data":"anId";
  "anotherdata": "another value"
}
```

RPC ориентирован на предоставление поведения (behaviors). RPC часто используют во внутренних коммуникациях ради производительности — так можно вручную написать нативные вызовы, точно подогнанные под ваш сценарий использования.

Выбирайте нативную библиотеку (она же SDK), когда:

* Вы точно знаете целевую платформу.
* Вы хотите сами контролировать способ доступа к своей «логике».
* Вы хотите сами определять, как обрабатываются ошибки за пределами библиотеки.
* Производительность и опыт конечного пользователя — ваш главный приоритет.

HTTP API, следующие стилю **REST**, чаще используют для публичных API.

#### Недостатки: RPC

* RPC-клиенты оказываются тесно связаны (tightly coupled) с реализацией сервиса.
* Под каждую новую операцию или сценарий использования нужно описывать новый API.
* RPC может быть сложно отлаживать.
* Не всегда получится использовать существующие технологии «из коробки». Например, может потребоваться дополнительная работа, чтобы [RPC-вызовы корректно кэшировались](https://web.archive.org/web/20170608193645/http://etherealbits.com/2012/12/debunking-the-myths-of-rpc-rest/) на таких кэширующих серверах, как [Squid](http://www.squid-cache.org/).

### Передача состояния представления (REST)

REST — это архитектурный стиль, который навязывает модель клиент/сервер: клиент работает с набором ресурсов, управляемых сервером. Сервер предоставляет представление ресурсов и действия, позволяющие изменить ресурс или получить его новое представление. Всё взаимодействие должно быть без сохранения состояния (stateless) и кэшируемым.

У RESTful-интерфейса есть четыре свойства:

* **Идентификация ресурсов (URI в HTTP)** — используйте один и тот же URI независимо от операции.
* **Изменение через представления (глаголы в HTTP)** — используйте глаголы, заголовки и тело запроса.
* **Самоописываемые сообщения об ошибках (коды статуса в HTTP)** — используйте коды состояния, не изобретайте велосипед.
* **[HATEOAS](http://restcookbook.com/Basics/hateoas/) (HTML-интерфейс для HTTP)** — ваш веб-сервис должен быть полностью доступен через браузер.

Пример REST-вызовов:

```
GET /someresources/anId

PUT /someresources/anId
{"anotherdata": "another value"}
```

REST ориентирован на предоставление данных. Он минимизирует связанность между клиентом и сервером и часто используется для публичных HTTP API. REST использует более общий и единообразный способ работы с ресурсами: через URI, [представление через заголовки](https://github.com/for-GET/know-your-http-well/blob/master/headers.md) и действия через такие глаголы, как GET, POST, PUT, DELETE и PATCH. Благодаря отсутствию состояния (statelessness) REST отлично подходит для горизонтального масштабирования и партиционирования.

#### Недостатки: REST

* Поскольку REST ориентирован на данные, он не очень подходит, если ресурсы не организованы естественным образом в простую иерархию. Например, вернуть все записи, обновлённые за последний час и соответствующие определённому набору событий, не так просто выразить через путь (path). В REST это обычно реализуют комбинацией пути URI, параметров запроса и, возможно, тела запроса.
* REST обычно опирается на небольшой набор глаголов (GET, POST, PUT, DELETE, PATCH), и иногда они плохо ложатся на ваш сценарий. Например, перенос просроченных документов в архивную папку не очень чисто вписывается в эти глаголы.
* Получение сложных ресурсов с вложенной иерархией требует нескольких обращений между клиентом и сервером, чтобы собрать одно представление — например, получить содержимое записи блога и комментарии к ней. Для мобильных приложений, работающих в нестабильной сети, множественные обращения крайне нежелательны.
* Со временем в ответ API могут добавляться новые поля, и старые клиенты будут получать все новые данные — даже те, что им не нужны. Это раздувает размер полезной нагрузки (payload) и увеличивает задержки.

### Сравнение вызовов RPC и REST

| Операция | RPC | REST |
|---|---|---|
| Регистрация    | **POST** /signup | **POST** /persons |
| Увольнение    | **POST** /resign<br/>{<br/>"personid": "1234"<br/>} | **DELETE** /persons/1234 |
| Получить данные пользователя | **GET** /readPerson?personid=1234 | **GET** /persons/1234 |
| Получить список предметов пользователя | **GET** /readUsersItemsList?personid=1234 | **GET** /persons/1234/items |
| Добавить предмет в список пользователя | **POST** /addItemToUsersItemsList<br/>{<br/>"personid": "1234";<br/>"itemid": "456"<br/>} | **POST** /persons/1234/items<br/>{<br/>"itemid": "456"<br/>} |
| Обновить предмет    | **POST** /modifyItem<br/>{<br/>"itemid": "456";<br/>"key": "value"<br/>} | **PUT** /items/456<br/>{<br/>"key": "value"<br/>} |
| Удалить предмет | **POST** /removeItem<br/>{<br/>"itemid": "456"<br/>} | **DELETE** /items/456 |
