Без интервьюера, которому можно задать уточняющие вопросы, мы сами определим сценарии использования и ограничения.

### Сценарии использования

#### Ограничим задачу следующими сценариями

* **Пользователь** подключает финансовый счёт
* **Сервис** извлекает транзакции по счёту
    * Ежедневное обновление
    * Категоризация транзакций
        * Пользователь может вручную переопределить категорию
        * Автоматической повторной категоризации нет
    * Анализ ежемесячных трат по категориям
* **Сервис** рекомендует бюджет
    * Пользователи могут вручную задать бюджет
    * Отправляет уведомления при приближении к бюджету или его превышении
* **Сервис** обладает высокой доступностью

#### Вне рамок задачи

* **Сервис** ведёт дополнительное логирование и аналитику

### Ограничения и допущения

#### Проговорим допущения

* Трафик распределён неравномерно
* Автоматическое ежедневное обновление счетов касается только пользователей, активных за последние 30 дней
* Добавление или удаление финансовых счетов — довольно редкое событие
* Уведомления о бюджете не обязаны приходить мгновенно
* 10 миллионов пользователей
    * 10 категорий бюджета на пользователя = 100 миллионов элементов бюджета
    * Примеры категорий:
        * Жильё = $1,000
        * Еда = $200
        * Бензин = $100
    * Категория транзакции определяется по продавцу
        * 50,000 продавцов
* 30 миллионов финансовых счетов
* 5 миллиардов транзакций в месяц
* 500 миллионов запросов на чтение в месяц
* Соотношение записи к чтению — 10:1
    * Профиль нагрузки смещён в сторону записи: пользователи совершают транзакции ежедневно, но заходят на сайт далеко не каждый день

#### Прикинем нагрузку

**Уточни у интервьюера, нужно ли делать расчёты на салфетке по использованию.**

* Размер одной транзакции:
    * `user_id` — 8 байт
    * `created_at` — 5 байт
    * `seller` — 32 байта
    * `amount` — 5 байт
    * Итого: ~50 байт
* 250 ГБ новых данных о транзакциях в месяц
    * 50 bytes per transaction * 5 billion transactions per month
    * 9 ТБ новых данных о транзакциях за 3 года
    * Предполагаем, что большинство записей — новые транзакции, а не обновления существующих
* 2,000 транзакций в секунду в среднем
* 200 запросов на чтение в секунду в среднем

Шпаргалка по пересчёту:

* 2.5 million seconds per month
* 1 request per second = 2.5 million requests per month
* 40 requests per second = 100 million requests per month
* 400 requests per second = 1 billion requests per month

### Сценарий: пользователь подключает финансовый счёт

Информацию о 10 миллионах пользователей можно хранить в [[Реляционные БД (RDBMS)|реляционной базе данных]]. Стоит обсудить [сценарии использования и компромиссы между выбором SQL или NoSQL](https://github.com/donnemartin/system-design-primer#sql-or-nosql).

* **Клиент** отправляет запрос **веб-серверу**, работающему как [[Обратный прокси|обратный прокси]]
* **Веб-сервер** пересылает запрос серверу **Accounts API**
* Сервер **Accounts API** обновляет таблицу `accounts` в **SQL-базе**, добавляя туда данные только что введённого счёта

**Уточни у интервьюера, сколько кода от тебя ожидают написать**.

Таблица `accounts` могла бы иметь такую структуру:

```
id int NOT NULL AUTO_INCREMENT
created_at datetime NOT NULL
last_update datetime NOT NULL
account_url varchar(255) NOT NULL
account_login varchar(32) NOT NULL
account_password_hash char(64) NOT NULL
user_id int NOT NULL
PRIMARY KEY(id)
FOREIGN KEY(user_id) REFERENCES users(id)
```

Создадим [индекс](https://github.com/donnemartin/system-design-primer#use-good-indices) по `id`, `user_id` и `created_at`, чтобы ускорить поиск (логарифмическое время вместо сканирования всей таблицы) и удержать данные в памяти. Последовательное чтение 1 МБ из памяти занимает около 250 микросекунд, тогда как с SSD это в 4 раза дольше, а с диска — в 80 раз дольше.<sup><a href=https://github.com/donnemartin/system-design-primer#latency-numbers-every-programmer-should-know>1</a></sup>

Мы используем публичный [[RPC и REST|REST API]]:

```
$ curl -X POST --data '{ "user_id": "foo", "account_url": "bar", \
    "account_login": "baz", "account_password": "qux" }' \
    https://mint.com/api/v1/account
```

Для внутренних коммуникаций можно использовать [[RPC и REST|удалённый вызов процедур (RPC)]].

Дальше сервис извлекает транзакции по счёту.

### Сценарий: сервис извлекает транзакции по счёту

Извлекать информацию по счёту нужно в следующих случаях:

* Пользователь впервые привязывает счёт
* Пользователь вручную обновляет счёт
* Автоматически каждый день — для пользователей, активных за последние 30 дней

Поток данных:

* **Клиент** отправляет запрос **веб-серверу**
* **Веб-сервер** пересылает запрос серверу **Accounts API**
* Сервер **Accounts API** кладёт задание в **очередь** — например, [Amazon SQS](https://aws.amazon.com/sqs/) или [RabbitMQ](https://www.rabbitmq.com/)
    * Извлечение транзакций может занять время, так что это, вероятно, стоит делать [[Асинхронность|асинхронно через очередь]] — хотя это добавляет сложности
* **Сервис извлечения транзакций** делает следующее:
    * Забирает задание из **очереди** и извлекает транзакции по указанному счёту из финансовой организации, сохраняя результаты как сырые лог-файлы в **object store**
    * Использует **Category Service**, чтобы категоризировать каждую транзакцию
    * Использует **Budget Service**, чтобы посчитать суммарные ежемесячные траты по категориям
        * **Budget Service** использует **Notification Service**, чтобы сообщить пользователям, что они приближаются к бюджету или превысили его
    * Обновляет таблицу `transactions` в **SQL-базе** категоризированными транзакциями
    * Обновляет таблицу `monthly_spending` в **SQL-базе** агрегированными ежемесячными тратами по категориям
    * Уведомляет пользователя о завершении обработки транзакций через **Notification Service**:
        * Для асинхронной отправки уведомлений используется **очередь** (не показана на схеме)

Таблица `transactions` могла бы иметь такую структуру:

```
id int NOT NULL AUTO_INCREMENT
created_at datetime NOT NULL
seller varchar(32) NOT NULL
amount decimal NOT NULL
user_id int NOT NULL
PRIMARY KEY(id)
FOREIGN KEY(user_id) REFERENCES users(id)
```

Создадим [индекс](https://github.com/donnemartin/system-design-primer#use-good-indices) по `id`, `user_id` и `created_at`.

Таблица `monthly_spending` могла бы иметь такую структуру:

```
id int NOT NULL AUTO_INCREMENT
month_year date NOT NULL
category varchar(32)
amount decimal NOT NULL
user_id int NOT NULL
PRIMARY KEY(id)
FOREIGN KEY(user_id) REFERENCES users(id)
```

Создадим [индекс](https://github.com/donnemartin/system-design-primer#use-good-indices) по `id` и `user_id`.

#### Category service

Для **Category Service** можно засеять словарь «продавец → категория» самыми популярными продавцами. Если оценить число продавцов в 50,000, а каждую запись — менее чем в 255 байт, весь словарь займёт около 12 МБ памяти.

**Уточни у интервьюера, сколько кода от тебя ожидают написать**.

```python
class DefaultCategories(Enum):

    HOUSING = 0
    FOOD = 1
    GAS = 2
    SHOPPING = 3
    ...

seller_category_map = {}
seller_category_map['Exxon'] = DefaultCategories.GAS
seller_category_map['Target'] = DefaultCategories.SHOPPING
...
```

Для продавцов, изначально не попавших в словарь, можно задействовать краудсорсинг: оценивать ручные переопределения категорий, которые вносят пользователи. Чтобы за O(1) быстро находить самое популярное ручное переопределение по продавцу, подойдёт куча (heap).

```python
class Categorizer(object):

    def __init__(self, seller_category_map, seller_category_crowd_overrides_map):
        self.seller_category_map = seller_category_map
        self.seller_category_crowd_overrides_map = \
            seller_category_crowd_overrides_map

    def categorize(self, transaction):
        if transaction.seller in self.seller_category_map:
            return self.seller_category_map[transaction.seller]
        elif transaction.seller in self.seller_category_crowd_overrides_map:
            self.seller_category_map[transaction.seller] = \
                self.seller_category_crowd_overrides_map[transaction.seller].peek_min()
            return self.seller_category_map[transaction.seller]
        return None
```

Реализация транзакции:

```python
class Transaction(object):

    def __init__(self, created_at, seller, amount):
        self.created_at = created_at
        self.seller = seller
        self.amount = amount
```

### Сценарий: сервис рекомендует бюджет

Для начала можно использовать типовой шаблон бюджета, который распределяет суммы по категориям в зависимости от уровня дохода. Такой подход избавляет от необходимости хранить все 100 миллионов элементов бюджета из ограничений — достаточно хранить только те, что пользователь переопределил вручную. Если пользователь переопределяет категорию бюджета, переопределение можно сохранить в `TABLE budget_overrides`.

```python
class Budget(object):

    def __init__(self, income):
        self.income = income
        self.categories_to_budget_map = self.create_budget_template()

    def create_budget_template(self):
        return {
            DefaultCategories.HOUSING: self.income * .4,
            DefaultCategories.FOOD: self.income * .2,
            DefaultCategories.GAS: self.income * .1,
            DefaultCategories.SHOPPING: self.income * .2,
            ...
        }

    def override_category_budget(self, category, amount):
        self.categories_to_budget_map[category] = amount
```

Для **Budget Service** можно, в принципе, выполнять SQL-запросы к таблице `transactions`, чтобы формировать агрегированную таблицу `monthly_spending`. В таблице `monthly_spending` строк будет заметно меньше, чем в общей массе из 5 миллиардов транзакций, поскольку у пользователя обычно много транзакций за месяц.

Как альтернативу можно запускать **MapReduce**-задания над сырыми файлами транзакций, чтобы:

* Категоризировать каждую транзакцию
* Сформировать агрегированные ежемесячные траты по категориям

Анализ файлов транзакций вместо прямых запросов к базе способен заметно снизить нагрузку на неё.

**Budget Service** можно вызывать повторно, если пользователь обновил категорию, — чтобы пересчитать анализ.

**Уточни у интервьюера, сколько кода от тебя ожидают написать**.

Пример формата лог-файла, с разделителями-табуляциями:

```
user_id   timestamp   seller  amount
```

Реализация **MapReduce**:

```python
class SpendingByCategory(MRJob):

    def __init__(self, categorizer):
        self.categorizer = categorizer
        self.current_year_month = calc_current_year_month()
        ...

    def calc_current_year_month(self):
        """Return the current year and month."""
        ...

    def extract_year_month(self, timestamp):
        """Return the year and month portions of the timestamp."""
        ...

    def handle_budget_notifications(self, key, total):
        """Call notification API if nearing or exceeded budget."""
        ...

    def mapper(self, _, line):
        """Parse each log line, extract and transform relevant lines.

        Argument line will be of the form:

        user_id   timestamp   seller  amount

        Using the categorizer to convert seller to category,
        emit key value pairs of the form:

        (user_id, 2016-01, shopping), 25
        (user_id, 2016-01, shopping), 100
        (user_id, 2016-01, gas), 50
        """
        user_id, timestamp, seller, amount = line.split('\t')
        category = self.categorizer.categorize(seller)
        period = self.extract_year_month(timestamp)
        if period == self.current_year_month:
            yield (user_id, period, category), amount

    def reducer(self, key, value):
        """Sum values for each key.

        (user_id, 2016-01, shopping), 125
        (user_id, 2016-01, gas), 50
        """
        total = sum(values)
        yield key, sum(values)
```

Добавим ещё один сценарий: **пользователь** просматривает сводки и транзакции.

Пользовательские сессии, агрегированную статистику по категориям и недавние транзакции можно разместить в **кэше в памяти** — например, Redis или Memcached.

* **Клиент** отправляет запрос на чтение **веб-серверу**
* **Веб-сервер** пересылает запрос серверу **Read API**
    * Статический контент можно отдавать из **object store**, например S3, который кэшируется на **CDN**
* Сервер **Read API** делает следующее:
    * Проверяет **кэш в памяти** на наличие контента
        * Если url есть в **кэше в памяти**, возвращает содержимое из кэша
        * Иначе
            * Если url есть в **SQL-базе**, получает содержимое оттуда
                * Обновляет **кэш в памяти** этим содержимым

За компромиссами и альтернативами обращайся к разделу [[Кэш#Когда обновлять кэш|«Когда обновлять кэш»]]. Описанный выше подход — это [[Кэш#Cache-aside|cache-aside]].

Вместо того чтобы держать агрегированную таблицу `monthly_spending` в **SQL-базе**, можно вынести её в отдельную **аналитическую базу данных**, построенную на решении для data warehousing — например, Amazon Redshift или Google BigQuery.

Возможно, стоит хранить в базе только месяц данных `transactions`, а остальное — в data warehouse или в **object store**. **Object store**, например Amazon S3, спокойно справится с ограничением в 250 ГБ нового контента в месяц.

Чтобы справиться со *средними* 200 запросами на чтение в секунду (на пике больше), трафик к популярному контенту должен обрабатываться **кэшем в памяти**, а не базой. **Кэш в памяти** также полезен для сглаживания неравномерного трафика и всплесков нагрузки. **SQL read-реплики** должны справляться с промахами кэша — при условии, что реплики не перегружены репликацией записей.

2,000 *средних* записей транзакций в секунду (на пике больше) может оказаться серьёзной нагрузкой для одного **SQL write master-slave**. Возможно, понадобятся дополнительные паттерны масштабирования SQL:

* [[Базы данных|Федерализация]]
* [[Базы данных|Шардирование]]
* [[Базы данных|Денормализация]]
* [[Базы данных|Тюнинг SQL]]

Также стоит рассмотреть перенос части данных в **NoSQL-базу**.
