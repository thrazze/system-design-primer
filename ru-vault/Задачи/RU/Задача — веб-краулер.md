# Задача — веб-краулер

*Примечание: этот документ ссылается напрямую на соответствующие разделы [тем системного дизайна](https://github.com/donnemartin/system-design-primer#index-of-system-design-topics), чтобы избежать дублирования. За общими тезисами, компромиссами и альтернативами обращайтесь к материалам по ссылкам.*

## Шаг 1: Очертить сценарии использования и ограничения

> Собери требования и определи границы задачи.
> Задавай уточняющие вопросы про сценарии использования и ограничения.
> Обсуди допущения.

Без интервьюера, которому можно задать уточняющие вопросы, определим сценарии использования и ограничения сами.

### Сценарии использования

#### Ограничим задачу следующими сценариями

* **Сервис** обходит список url:
    * Генерирует обратный индекс слов по страницам, содержащим поисковые термины
    * Генерирует заголовки и сниппеты для страниц
        * Заголовок и сниппет статичны, они не меняются в зависимости от поискового запроса
* **Пользователь** вводит поисковый запрос и видит список релевантных страниц с заголовками и сниппетами, сгенерированными краулером
    * Для этого сценария набросаем только компоненты верхнего уровня и их взаимодействие, без глубокой детализации
* **Сервис** обладает высокой доступностью

#### Вне рамок задачи

* Аналитика поиска
* Персонализированные результаты поиска
* Ранжирование страниц (page rank)

### Ограничения и допущения

#### Формулируем допущения

* Трафик распределён неравномерно
    * Одни запросы очень популярны, другие выполняются лишь однажды
* Поддерживаем только анонимных пользователей
* Генерация результатов поиска должна быть быстрой
* Веб-краулер не должен зацикливаться
    * Мы зациклимся, если граф содержит цикл
* 1 миллиард ссылок для обхода
    * Страницы нужно обходить регулярно, чтобы поддерживать актуальность
    * Средняя частота обновления — примерно раз в неделю, для популярных сайтов чаще
        * 4 миллиарда ссылок обходится в месяц
    * Средний размер хранимой веб-страницы: 500 KB
        * Для простоты считаем изменения как новые страницы
* 100 миллиардов поисковых запросов в месяц

Потренируемся использовать более традиционные системы — не будем опираться на готовые решения вроде [solr](http://lucene.apache.org/solr/) или [nutch](http://nutch.apache.org/).

#### Прикидываем нагрузку

**Уточни у интервьюера, нужно ли делать расчёты на салфетке по нагрузке.**

* 2 PB хранимого контента страниц в месяц
    * 500 KB per page * 4 billion links crawled per month
    * 72 PB хранимого контента страниц за 3 года
* 1,600 запросов на запись в секунду
* 40,000 поисковых запросов в секунду

Памятка по пересчёту:

* 2,5 миллиона секунд в месяц
* 1 request per second = 2.5 million requests per month
* 40 requests per second = 100 million requests per month
* 400 requests per second = 1 billion requests per month

## Шаг 3: Спроектировать ключевые компоненты

> Углубись в детали каждого ключевого компонента.

### Сценарий: Сервис обходит список url

Будем считать, что у нас уже есть исходный список `links_to_crawl`, изначально ранжированный по общей популярности сайта. Если это допущение неразумно, можно засеять краулер популярными сайтами, которые ссылаются на внешний контент — например, [Yahoo](https://www.yahoo.com/), [DMOZ](http://www.dmoz.org/) и т. д.

Для хранения обработанных ссылок и их сигнатур страниц будем использовать таблицу `crawled_links`.

`links_to_crawl` и `crawled_links` можно хранить в **NoSQL-базе** «ключ-значение». Для ранжированных ссылок в `links_to_crawl` подойдёт [Redis](https://redis.io/) с sorted sets — так можно поддерживать ранжирование ссылок на страницы. Стоит обсудить [сценарии использования и компромиссы выбора между SQL и NoSQL](https://github.com/donnemartin/system-design-primer#sql-or-nosql).

* **Crawler Service** обрабатывает каждую ссылку на страницу циклом:
    * Берёт ссылку с наивысшим приоритетом
        * Проверяет `crawled_links` в **NoSQL-базе** на наличие записи с похожей сигнатурой страницы
            * Если похожая страница уже есть, снижает приоритет этой ссылки
                * Это предотвращает зацикливание
                * Continue
            * Иначе обходит ссылку
                * Добавляет задачу в очередь **Reverse Index Service** на генерацию [обратного индекса](https://en.wikipedia.org/wiki/Search_engine_indexing)
                * Добавляет задачу в очередь **Document Service** на генерацию статичного заголовка и сниппета
                * Генерирует сигнатуру страницы
                * Удаляет ссылку из `links_to_crawl` в **NoSQL-базе**
                * Вставляет ссылку и сигнатуру в `crawled_links` в **NoSQL-базе**

**Уточни у интервьюера, сколько кода от тебя ожидают написать**.

`PagesDataStore` — абстракция внутри **Crawler Service**, использующая **NoSQL-базу**:

```python
class PagesDataStore(object):

    def __init__(self, db);
        self.db = db
        ...

    def add_link_to_crawl(self, url):
        """Add the given link to `links_to_crawl`."""
        ...

    def remove_link_to_crawl(self, url):
        """Remove the given link from `links_to_crawl`."""
        ...

    def reduce_priority_link_to_crawl(self, url)
        """Reduce the priority of a link in `links_to_crawl` to avoid cycles."""
        ...

    def extract_max_priority_page(self):
        """Return the highest priority link in `links_to_crawl`."""
        ...

    def insert_crawled_link(self, url, signature):
        """Add the given link to `crawled_links`."""
        ...

    def crawled_similar(self, signature):
        """Determine if we've already crawled a page matching the given signature"""
        ...
```

`Page` — абстракция внутри **Crawler Service**, инкапсулирующая страницу, её содержимое, дочерние url и сигнатуру:

```python
class Page(object):

    def __init__(self, url, contents, child_urls, signature):
        self.url = url
        self.contents = contents
        self.child_urls = child_urls
        self.signature = signature
```

`Crawler` — главный класс **Crawler Service**, состоящий из `Page` и `PagesDataStore`.

```python
class Crawler(object):

    def __init__(self, data_store, reverse_index_queue, doc_index_queue):
        self.data_store = data_store
        self.reverse_index_queue = reverse_index_queue
        self.doc_index_queue = doc_index_queue

    def create_signature(self, page):
        """Create signature based on url and contents."""
        ...

    def crawl_page(self, page):
        for url in page.child_urls:
            self.data_store.add_link_to_crawl(url)
        page.signature = self.create_signature(page)
        self.data_store.remove_link_to_crawl(page.url)
        self.data_store.insert_crawled_link(page.url, page.signature)

    def crawl(self):
        while True:
            page = self.data_store.extract_max_priority_page()
            if page is None:
                break
            if self.data_store.crawled_similar(page.signature):
                self.data_store.reduce_priority_link_to_crawl(page.url)
            else:
                self.crawl_page(page)
```

### Обработка дубликатов

Нужно позаботиться о том, чтобы веб-краулер не зациклился — это происходит, когда граф содержит цикл.

**Уточни у интервьюера, сколько кода от тебя ожидают написать**.

Дубликаты url нужно удалять:

* Для небольших списков подойдёт что-то вроде `sort | unique`
* При 1 миллиарде ссылок для обхода можно использовать **MapReduce**, чтобы вывести только записи с частотой 1

```python
class RemoveDuplicateUrls(MRJob):

    def mapper(self, _, line):
        yield line, 1

    def reducer(self, key, values):
        total = sum(values)
        if total == 1:
            yield key, total
```

Обнаружение дублирующегося контента — задача сложнее. Можно сгенерировать сигнатуру на основе содержимого страницы и сравнивать две сигнатуры на схожесть. Среди подходящих алгоритмов — [индекс Жаккара](https://en.wikipedia.org/wiki/Jaccard_index) и [косинусное сходство](https://en.wikipedia.org/wiki/Cosine_similarity).

### Определение момента обновления результатов обхода

Страницы нужно обходить регулярно, чтобы поддерживать актуальность. У результатов обхода может быть поле `timestamp`, отмечающее время последнего обхода страницы. По истечении периода по умолчанию — скажем, одной недели — все страницы должны обновляться. Часто обновляемые или более популярные сайты можно обновлять с меньшим интервалом.

Хотя мы не будем углубляться в аналитику, можно провести анализ данных, чтобы определить среднее время до обновления конкретной страницы, и использовать эту статистику для определения частоты повторного обхода.

Также можно поддержать файл `Robots.txt`, дающий владельцам сайтов контроль над частотой обхода.

### Сценарий: Пользователь вводит поисковый запрос и видит список релевантных страниц с заголовками и сниппетами

* **Клиент** отправляет запрос на **Web Server**, работающий как [обратный прокси](https://github.com/donnemartin/system-design-primer#reverse-proxy-web-server)
* **Web Server** пересылает запрос серверу **Query API**
* Сервер **Query API** делает следующее:
    * Разбирает запрос
        * Убирает разметку
        * Разбивает текст на термины
        * Исправляет опечатки
        * Нормализует регистр
        * Преобразует запрос в булевы операции
    * Использует **Reverse Index Service** для поиска документов, соответствующих запросу
        * **Reverse Index Service** ранжирует найденные результаты и возвращает лучшие
    * Использует **Document Service** для получения заголовков и сниппетов

Будем использовать публичный [**REST API**](https://github.com/donnemartin/system-design-primer#representational-state-transfer-rest):

```
$ curl https://search.com/api/v1/search?query=hello+world
```

Ответ:

```
{
    "title": "foo's title",
    "snippet": "foo's snippet",
    "link": "https://foo.com",
},
{
    "title": "bar's title",
    "snippet": "bar's snippet",
    "link": "https://bar.com",
},
{
    "title": "baz's title",
    "snippet": "baz's snippet",
    "link": "https://baz.com",
},
```

Для внутренних коммуникаций можно использовать [удалённый вызов процедур](https://github.com/donnemartin/system-design-primer#remote-procedure-call-rpc).

## Шаг 4: Масштабировать дизайн

> Определи узкие места и устрани их с учётом ограничений.

![Imgur](http://i.imgur.com/bWxPtQA.png)

**Важно: не переходи сразу от исходного дизайна к финальному!**

Проговори, что ты будешь: 1) **бенчмаркать/нагрузочно тестировать**, 2) **профилировать** узкие места, 3) устранять узкие места, оценивая альтернативы и компромиссы, и 4) повторять цикл. Смотри [[Задача — масштабирование до миллионов пользователей на AWS|Design a system that scales to millions of users on AWS]] как пример итеративного масштабирования исходного дизайна.

Важно обсудить, какие узкие места могут возникнуть в исходном дизайне и как их устранить. Например, какие проблемы решает добавление **балансировщика нагрузки** с несколькими **веб-серверами**? **CDN**? **Master-Slave-репликами**? Какие есть альтернативы и **компромиссы** для каждого из этих решений?

Добавим несколько компонентов, чтобы завершить дизайн и решить проблемы масштабируемости. Внутренние балансировщики нагрузки на схеме не показаны — чтобы не загромождать её.

*Чтобы не повторять уже раскрытые темы*, обратись к следующим [темам системного дизайна](https://github.com/donnemartin/system-design-primer#index-of-system-design-topics) за основными тезисами, компромиссами и альтернативами:

* [[Система доменных имён (DNS)|DNS]]
* [[Балансировщик нагрузки|Load balancer]]
* [Горизонтальное масштабирование](https://github.com/donnemartin/system-design-primer#horizontal-scaling)
* [[Обратный прокси|Web server (reverse proxy)]]
* [[Уровень приложений|API server (application layer)]]
* [[Кэш|Cache]]
* [[NoSQL — типы хранилищ|NoSQL]]
* [[Шаблоны согласованности|Consistency patterns]]
* [[Шаблоны доступности|Availability patterns]]

Одни запросы очень популярны, другие выполняются лишь однажды. Популярные запросы можно отдавать из **кэша в памяти**, такого как Redis или Memcached, — это сокращает время отклика и снижает нагрузку на **Reverse Index Service** и **Document Service**. **Кэш в памяти** также полезен для сглаживания неравномерно распределённого трафика и его всплесков. Последовательное чтение 1 МБ из памяти занимает около 250 микросекунд, тогда как чтение с SSD занимает в 4 раза дольше, а с диска — в 80 раз дольше.<sup><a href=https://github.com/donnemartin/system-design-primer#latency-numbers-every-programmer-should-know>1</a></sup>

Ниже — ещё несколько оптимизаций для **Crawling Service**:

* Чтобы справиться с объёмом данных и нагрузкой по запросам, **Reverse Index Service** и **Document Service**, скорее всего, потребуют активного использования шардирования и федерализации.
* DNS-запросы могут стать узким местом; **Crawler Service** может держать собственный кэш DNS-запросов, периодически обновляемый
* **Crawler Service** может повысить производительность и снизить потребление памяти, держа открытыми множество соединений одновременно — это называется [пулом соединений](https://en.wikipedia.org/wiki/Connection_pool) (connection pooling)
    * Переход на [[TCP и UDP|UDP]] также может повысить производительность
* Обход веба требует много пропускной способности сети — убедись, что её достаточно для поддержания высокой пропускной способности
