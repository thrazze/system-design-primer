### Сценарий: пользователь ищет человека и видит кратчайший путь до найденного человека

**Уточни у интервьюера, сколько кода от тебя ожидают**.

Если бы не ограничение в миллионы пользователей (вершин) и миллиарды дружеских связей (рёбер), эту задачу поиска кратчайшего пути без весов можно было бы решить обычным BFS-подходом:

```python
class Graph(Graph):

    def shortest_path(self, source, dest):
        if source is None or dest is None:
            return None
        if source is dest:
            return [source.key]
        prev_node_keys = self._shortest_path(source, dest)
        if prev_node_keys is None:
            return None
        else:
            path_ids = [dest.key]
            prev_node_key = prev_node_keys[dest.key]
            while prev_node_key is not None:
                path_ids.append(prev_node_key)
                prev_node_key = prev_node_keys[prev_node_key]
            return path_ids[::-1]

    def _shortest_path(self, source, dest):
        queue = deque()
        queue.append(source)
        prev_node_keys = {source.key: None}
        source.visit_state = State.visited
        while queue:
            node = queue.popleft()
            if node is dest:
                return prev_node_keys
            prev_node = node
            for adj_node in node.adj_nodes.values():
                if adj_node.visit_state == State.unvisited:
                    queue.append(adj_node)
                    prev_node_keys[adj_node.key] = prev_node.key
                    adj_node.visit_state = State.visited
        return None
```

Все пользователи не поместятся на одной машине, поэтому нужно [шардировать](https://github.com/donnemartin/system-design-primer#sharding) их по **Person Server**'ам и обращаться к ним через **Lookup Service**.

* **Client** отправляет запрос на **Web Server**, работающий как [обратный прокси](https://github.com/donnemartin/system-design-primer#reverse-proxy-web-server)
* **Web Server** пересылает запрос серверу **Search API**
* **Search API** пересылает запрос в **User Graph Service**
* **User Graph Service** делает следующее:
    * Использует **Lookup Service**, чтобы найти **Person Server**, на котором хранится информация о текущем пользователе
    * Находит нужный **Person Server**, чтобы получить список `friend_ids` текущего пользователя
    * Запускает BFS-поиск, где текущий пользователь — это `source`, а его `friend_ids` — идентификаторы для каждого `adjacent_node`
    * Чтобы получить `adjacent_node` по идентификатору:
        * **User Graph Service** *снова* обращается к **Lookup Service**, чтобы определить, на каком **Person Server** хранится `adjacent_node` с нужным id (потенциальное место для оптимизации)

**Уточни у интервьюера, сколько кода тебе стоит написать**.

**Примечание**: для простоты обработка ошибок ниже опущена. Уточни, нужно ли реализовывать её по-настоящему.

**Реализация Lookup Service**:

```python
class LookupService(object):

    def __init__(self):
        self.lookup = self._init_lookup()  # key: person_id, value: person_server

    def _init_lookup(self):
        ...

    def lookup_person_server(self, person_id):
        return self.lookup[person_id]
```

**Реализация Person Server**:

```python
class PersonServer(object):

    def __init__(self):
        self.people = {}  # key: person_id, value: person

    def add_person(self, person):
        ...

    def people(self, ids):
        results = []
        for id in ids:
            if id in self.people:
                results.append(self.people[id])
        return results
```

**Реализация Person**:

```python
class Person(object):

    def __init__(self, id, name, friend_ids):
        self.id = id
        self.name = name
        self.friend_ids = friend_ids
```

**Реализация User Graph Service**:

```python
class UserGraphService(object):

    def __init__(self, lookup_service):
        self.lookup_service = lookup_service

    def person(self, person_id):
        person_server = self.lookup_service.lookup_person_server(person_id)
        return person_server.people([person_id])

    def shortest_path(self, source_key, dest_key):
        if source_key is None or dest_key is None:
            return None
        if source_key is dest_key:
            return [source_key]
        prev_node_keys = self._shortest_path(source_key, dest_key)
        if prev_node_keys is None:
            return None
        else:
            # Iterate through the path_ids backwards, starting at dest_key
            path_ids = [dest_key]
            prev_node_key = prev_node_keys[dest_key]
            while prev_node_key is not None:
                path_ids.append(prev_node_key)
                prev_node_key = prev_node_keys[prev_node_key]
            # Reverse the list since we iterated backwards
            return path_ids[::-1]

    def _shortest_path(self, source_key, dest_key, path):
        # Use the id to get the Person
        source = self.person(source_key)
        # Update our bfs queue
        queue = deque()
        queue.append(source)
        # prev_node_keys keeps track of each hop from
        # the source_key to the dest_key
        prev_node_keys = {source_key: None}
        # We'll use visited_ids to keep track of which nodes we've
        # visited, which can be different from a typical bfs where
        # this can be stored in the node itself
        visited_ids = set()
        visited_ids.add(source.id)
        while queue:
            node = queue.popleft()
            if node.key is dest_key:
                return prev_node_keys
            prev_node = node
            for friend_id in node.friend_ids:
                if friend_id not in visited_ids:
                    friend_node = self.person(friend_id)
                    queue.append(friend_node)
                    prev_node_keys[friend_id] = prev_node.key
                    visited_ids.add(friend_id)
        return None
```

## Шаг 4: Масштабировать дизайн

> Найди узкие места с учётом ограничений и устрани их.

![Imgur](http://i.imgur.com/cdCv5g7.png)

**Важно: не перескакивай сразу от исходного дизайна к финальному!**

Проговори, что ты будешь: 1) **бенчмаркать/нагрузочно тестировать**, 2) **профилировать** в поисках узких мест, 3) устранять узкие места, оценивая альтернативы и компромиссы, и 4) повторять цикл. Пример итеративного масштабирования исходного дизайна смотри в [[Задача — масштабирование до миллионов пользователей на AWS|Design a system that scales to millions of users on AWS]].

Важно обсудить, какие узкие места могут возникнуть в исходном дизайне и как их устранить. Например, какие проблемы решает добавление **балансировщика нагрузки** с несколькими **Web Server**'ами? **CDN**? **master-slave-репликами**? Какие есть альтернативы и **компромиссы** у каждого решения?

Чтобы справиться с ограничением в 400 *средних* запросов на чтение в секунду (на пике больше), данные о людях можно отдавать из **Memory Cache** вроде Redis или Memcached — это сократит время отклика и снизит трафик к нижестоящим сервисам. Особенно это полезно для тех, кто делает несколько поисков подряд, и для хорошо связанных пользователей. Последовательное чтение 1 MB из памяти занимает около 250 микросекунд, тогда как с SSD это в 4 раза дольше, а с диска — в 80 раз дольше.<sup><a href=https://github.com/donnemartin/system-design-primer#latency-numbers-every-programmer-should-know>1</a></sup>

Дальнейшие оптимизации:

* Хранить полные или частичные BFS-обходы в **Memory Cache**, чтобы ускорить последующие запросы
* Считать пакетно в фоне (batch), а затем хранить полные или частичные BFS-обходы в **NoSQL Database**, чтобы ускорить последующие запросы
* Сократить число переходов между машинами, объединяя в один запрос поиски друзей, хранящихся на одном и том же **Person Server**
    * Дополнительно [шардировать](https://github.com/donnemartin/system-design-primer#sharding) **Person Server**'ы по географии, поскольку друзья обычно живут ближе друг к другу
* Запускать два BFS-поиска одновременно — один от источника, другой от цели — и затем объединять найденные пути
* Начинать BFS-поиск с людей, у которых много друзей: они с большей вероятностью сокращают число [степеней разделения](https://en.wikipedia.org/wiki/Six_degrees_of_separation) между текущим пользователем и целью поиска
* Установить лимит по времени или числу переходов, после которого спрашивать пользователя, хочет ли он продолжить поиск, — в некоторых случаях поиск может занять значительное время
* Использовать **графовую базу данных**, например [Neo4j](https://neo4j.com/), или специализированный язык запросов для графов вроде [GraphQL](http://graphql.org/) (если бы не было ограничения, запрещающего графовые базы данных)
