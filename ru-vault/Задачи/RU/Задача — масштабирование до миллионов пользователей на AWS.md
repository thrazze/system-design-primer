# Задача — масштабирование до миллионов пользователей на AWS

*Примечание: этот документ ссылается напрямую на соответствующие разделы [тем по системному дизайну](https://github.com/donnemartin/system-design-primer#index-of-system-design-topics), чтобы не дублировать материал. Общие тезисы, компромиссы и альтернативы смотри по ссылкам.*

## Шаг 1: Наметить сценарии использования и ограничения

> Собери требования и очерти границы задачи.
> Задавай вопросы, чтобы прояснить сценарии использования и ограничения.
> Обсуди допущения.

Раз рядом нет интервьюера, которому можно задать уточняющие вопросы, определим сценарии использования и ограничения самостоятельно.

### Сценарии использования

Решение этой задачи — итеративный процесс: 1) **бенчмарк/нагрузочное тестирование**, 2) **профилирование** узких мест, 3) устранение узких мест с оценкой альтернатив и компромиссов, и 4) повтор цикла. Это хороший паттерн для эволюции базовой архитектуры в масштабируемую.

Если у тебя нет опыта с AWS или ты не претендуешь на позицию, где знание AWS обязательно, детали, специфичные для AWS, не требуются. Однако **большинство принципов, разобранных в этом упражнении, применимы и за пределами экосистемы AWS.**

#### Ограничим задачу следующими сценариями использования

* **Пользователь** делает запрос на чтение или запись
    * **Сервис** обрабатывает его, сохраняет данные пользователя и возвращает результат
* **Сервису** нужно эволюционировать от обслуживания небольшого числа пользователей до миллионов
    * Обсудим общие паттерны масштабирования по мере того, как архитектура растёт, чтобы выдерживать большое число пользователей и запросов
* **Сервис** обладает высокой доступностью

### Ограничения и допущения

#### Сформулируем допущения

* Трафик распределён неравномерно
* Нужны реляционные данные
* Масштаб растёт от 1 пользователя до десятков миллионов
    * Обозначим рост числа пользователей как:
        * Users+
        * Users++
        * Users+++
        * …
    * 10 миллионов пользователей
    * 1 миллиард операций записи в месяц
    * 100 миллиардов операций чтения в месяц
    * соотношение чтения к записи 100:1
    * 1 КБ контента на одну запись

#### Посчитаем нагрузку

**Уточни у интервьюера, нужны ли расчёты на салфетке (back-of-the-envelope) по использованию.**

* 1 ТБ нового контента в месяц
    * 1 KB per write * 1 billion writes per month
    * 36 ТБ нового контента за 3 года
    * Предположим, что бо́льшая часть записей — это новый контент, а не обновления существующего
* 400 операций записи в секунду в среднем
* 40 000 операций чтения в секунду в среднем

Памятка по пересчёту:

* 2.5 million seconds per month
* 1 request per second = 2.5 million requests per month
* 40 requests per second = 100 million requests per month
* 400 requests per second = 1 billion requests per month

## Шаг 3: Спроектировать основные компоненты

> Углубись в детали каждого основного компонента.

### Сценарий использования: пользователь делает запрос на чтение или запись

#### Цели

* При 1-2 пользователях достаточно базовой конфигурации
    * Для простоты — один сервер
    * Вертикальное масштабирование по мере необходимости
    * Мониторинг для выявления узких мест

#### Начнём с одного сервера

* **Веб-сервер** на EC2
    * Хранилище для пользовательских данных
    * [**база данных MySQL**](https://github.com/donnemartin/system-design-primer#relational-database-management-system-rdbms)

Используем **вертикальное масштабирование (vertical scaling)**:

* Просто берём сервер помощнее
* Следим за метриками, чтобы понимать, куда масштабироваться
    * Базовый мониторинг для выявления узких мест: CPU, память, IO, сеть и т.д.
    * CloudWatch, top, nagios, statsd, graphite и т.д.
* Вертикальное масштабирование может обходиться очень дорого
* Нет резервирования / переключения при отказе (failover)

*Компромиссы, альтернативы и дополнительные детали:*

* Альтернатива **вертикальному масштабированию** — [**горизонтальное масштабирование (horizontal scaling)**](https://github.com/donnemartin/system-design-primer#horizontal-scaling)

#### Начнём с SQL, но будем держать в уме NoSQL

Согласно ограничениям, нужны реляционные данные. Начнём с **базы данных MySQL** на том же сервере.

*Компромиссы, альтернативы и дополнительные детали:*

* См. раздел [реляционные системы управления базами данных (RDBMS)](https://github.com/donnemartin/system-design-primer#relational-database-management-system-rdbms)
* Обсуждаем причины выбора [SQL или NoSQL](https://github.com/donnemartin/system-design-primer#sql-or-nosql)

#### Назначим публичный статический IP

* Elastic IP даёт публичный адрес, который не меняется при перезагрузке
* Это помогает с переключением при отказе (failover) — достаточно перенаправить домен на новый IP

#### Используем DNS

Добавляем **DNS**, например Route 53, чтобы связать домен с публичным IP инстанса.

*Компромиссы, альтернативы и дополнительные детали:*

* См. раздел [система доменных имён](https://github.com/donnemartin/system-design-primer#domain-name-system)

#### Защитим веб-сервер

* Открываем только нужные порты
    * Разрешаем веб-серверу отвечать на входящие запросы по:
        * 80 для HTTP
        * 443 для HTTPS
        * 22 для SSH — только с IP из белого списка
    * Запрещаем веб-серверу инициировать исходящие соединения

*Компромиссы, альтернативы и дополнительные детали:*

* См. раздел [безопасность](https://github.com/donnemartin/system-design-primer#security)

## Шаг 4: Масштабировать архитектуру

> Найди узкие места и устрани их с учётом ограничений.

### Users+

![Imgur](http://i.imgur.com/rrfjMXB.png)

#### Допущения

Число пользователей начинает расти, и нагрузка на наш единственный сервер увеличивается. **Бенчмарки/нагрузочные тесты** и **профилирование** показывают, что **база данных MySQL** занимает всё больше памяти и CPU, а пользовательский контент заполняет дисковое пространство.

Пока что мы решали эти проблемы **вертикальным масштабированием**. К сожалению, это становится довольно дорогим и не позволяет масштабировать **базу данных MySQL** и **веб-сервер** независимо друг от друга.

#### Цели

* Снять нагрузку с единственного сервера и дать возможность масштабировать компоненты независимо
    * Хранить статический контент отдельно, в **объектном хранилище (object store)**
    * Перенести **базу данных MySQL** на отдельный сервер
* Недостатки
    * Эти изменения усложняют систему и требуют правок в **веб-сервере**, чтобы он обращался к **объектному хранилищу** и **базе данных MySQL**
    * Нужны дополнительные меры безопасности для защиты новых компонентов
    * Расходы на AWS могут вырасти, но это стоит сравнивать с затратами на самостоятельное сопровождение аналогичных систем

#### Храним статический контент отдельно

* Стоит рассмотреть управляемое **объектное хранилище**, например S3, для статического контента
    * Высокая масштабируемость и надёжность
    * Шифрование на стороне сервера
* Переносим в S3
    * Пользовательские файлы
    * JS
    * CSS
    * Изображения
    * Видео

#### Переносим базу данных MySQL на отдельный сервер

* Стоит рассмотреть сервис вроде RDS для управления **базой данных MySQL**
    * Просто администрировать и масштабировать
    * Несколько зон доступности
    * Шифрование данных на диске (encryption at rest)

#### Защитим систему

* Шифруем данные при передаче и в состоянии покоя (in transit / at rest)
* Используем Virtual Private Cloud
    * Создаём публичную подсеть для единственного **веб-сервера**, чтобы он мог отправлять и принимать трафик из интернета
    * Создаём приватную подсеть для всего остального, закрыв доступ извне
    * Открываем порты только для IP из белого списка для каждого компонента
* Эти же паттерны нужно применять и к новым компонентам на протяжении всего дальнейшего разбора

*Компромиссы, альтернативы и дополнительные детали:*

* См. раздел [безопасность](https://github.com/donnemartin/system-design-primer#security)

### Users++

![Imgur](http://i.imgur.com/raoFTXM.png)

#### Допущения

**Бенчмарки/нагрузочные тесты** и **профилирование** показывают, что единственный **веб-сервер** становится узким местом в часы пик — ответы замедляются, а иногда сервис вообще падает. По мере взросления сервиса мы также хотим повысить доступность и резервирование.

#### Цели

* Следующие цели устраняют проблемы масштабирования **веб-сервера**
    * По результатам **бенчмарков/нагрузочных тестов** и **профилирования** может понадобиться реализовать лишь одну-две из этих техник
* Используем [**горизонтальное масштабирование**](https://github.com/donnemartin/system-design-primer#horizontal-scaling), чтобы справляться с растущей нагрузкой и устранить единые точки отказа
    * Добавляем [**балансировщик нагрузки**](https://github.com/donnemartin/system-design-primer#load-balancer), например Amazon ELB или HAProxy
        * ELB обладает высокой доступностью
        * При настройке собственного **балансировщика нагрузки** размещение нескольких серверов по схеме [активный-активный](https://github.com/donnemartin/system-design-primer#active-active) или [активный-пассивный](https://github.com/donnemartin/system-design-primer#active-passive) в разных зонах доступности повысит доступность
        * Терминируем SSL на **балансировщике нагрузки**, чтобы снизить вычислительную нагрузку на бэкенд-серверы и упростить администрирование сертификатов
    * Используем несколько **веб-серверов**, распределённых по разным зонам доступности
    * Используем несколько инстансов **MySQL** в режиме [**master-slave с переключением при отказе (failover)**](https://github.com/donnemartin/system-design-primer#master-slave-replication) в разных зонах доступности для повышения резервирования
* Отделяем **веб-серверы** от [**серверов приложений**](https://github.com/donnemartin/system-design-primer#application-layer)
    * Масштабируем и настраиваем оба слоя независимо
    * **Веб-серверы** могут работать как [**обратный прокси**](https://github.com/donnemartin/system-design-primer#reverse-proxy-web-server)
    * Например, можно выделить **серверы приложений**, обрабатывающие **API для чтения**, отдельно от тех, что обрабатывают **API для записи**
* Переносим статический (и часть динамического) контента в [**сеть доставки контента (CDN)**](https://github.com/donnemartin/system-design-primer#content-delivery-network), например CloudFront, чтобы снизить нагрузку и задержку

#### Допущения

**Бенчмарки/нагрузочные тесты** и **профилирование** показывают, что нагрузка у нас в основном на чтение (соотношение 100:1 с записью), и база данных страдает от низкой производительности из-за большого числа запросов на чтение.

#### Цели

* Следующие цели устраняют проблемы масштабирования **базы данных MySQL**
    * По результатам **бенчмарков/нагрузочных тестов** и **профилирования** может понадобиться реализовать лишь одну-две из этих техник
* Переносим следующие данные в [**кэш в памяти (memory cache)**](https://github.com/donnemartin/system-design-primer#cache), например Elasticache, чтобы снизить нагрузку и задержку:
    * Часто запрашиваемый контент из **MySQL**
        * Сначала стоит попробовать настроить кэш самой **базы данных MySQL** — возможно, этого хватит, чтобы снять узкое место, ещё до внедрения **кэша в памяти**
    * Данные сессий с **веб-серверов**
        * **Веб-серверы** становятся без состояния (stateless), что открывает дорогу **автомасштабированию**
    * Последовательное чтение 1 МБ из памяти занимает около 250 микросекунд, тогда как чтение с SSD — в 4 раза дольше, а с диска — в 80 раз дольше.<sup><a href=https://github.com/donnemartin/system-design-primer#latency-numbers-every-programmer-should-know>1</a></sup>
* Добавляем [**read-реплики MySQL**](https://github.com/donnemartin/system-design-primer#master-slave-replication), чтобы снизить нагрузку на master для записи
* Добавляем больше **веб-серверов** и **серверов приложений** для повышения отзывчивости

*Компромиссы, альтернативы и дополнительные детали:*

* Подробности — по ссылкам выше

#### Добавляем read-реплики MySQL

* Помимо добавления и масштабирования **кэша в памяти**, **read-реплики MySQL** тоже помогают снять нагрузку с **master MySQL для записи**
* Добавляем в **веб-сервер** логику, разделяющую запись и чтение
* Добавляем **балансировщики нагрузки** перед **read-репликами MySQL** (не показаны на схеме, чтобы не загромождать её)
* Большинство сервисов больше читают, чем пишут

### Users++++

![Imgur](http://i.imgur.com/3X8nmdL.png)

#### Допущения

**Бенчмарки/нагрузочные тесты** и **профилирование** показывают, что трафик резко растёт в рабочие часы в США и заметно падает, когда пользователи уходят из офиса. Мы полагаем, что можем сократить расходы, автоматически поднимая и выключая серверы в зависимости от реальной нагрузки. Мы небольшая компания, поэтому хотим максимально автоматизировать DevOps — и для **автомасштабирования**, и для повседневных операций.

#### Цели

* Добавляем **автомасштабирование**, чтобы выделять мощности по мере необходимости
    * Справляться со всплесками трафика
    * Снижать расходы, выключая неиспользуемые инстансы
* Автоматизируем DevOps
    * Chef, Puppet, Ansible и т.д.
* Продолжаем следить за метриками, чтобы устранять узкие места
    * **Уровень хоста** — состояние отдельного инстанса EC2
    * **Агрегированный уровень** — статистика балансировщика нагрузки
    * **Анализ логов** — CloudWatch, CloudTrail, Loggly, Splunk, Sumo
    * **Производительность с внешней точки зрения** — Pingdom или New Relic
    * **Обработка уведомлений и инцидентов** — PagerDuty
    * **Отчёты об ошибках** — Sentry

#### Добавляем автомасштабирование

* Стоит рассмотреть управляемый сервис вроде AWS **Auto Scaling**
    * Создаём одну группу для каждого **веб-сервера** и по одной для каждого типа **сервера приложений**, размещаем каждую группу в нескольких зонах доступности
    * Задаём минимальное и максимальное число инстансов
    * Триггер масштабирования вверх и вниз через CloudWatch
        * Простая метрика времени суток для предсказуемой нагрузки, либо
        * Метрики за период времени:
            * Загрузка CPU
            * Задержка
            * Сетевой трафик
            * Кастомная метрика
    * Недостатки
        * Автомасштабирование добавляет сложности
        * Системе может потребоваться время, чтобы адекватно нарастить мощности при росте спроса или снизить их при падении спроса

#### Допущения

По мере того как сервис продолжает расти к показателям, заданным в ограничениях, мы итеративно прогоняем **бенчмарки/нагрузочные тесты** и **профилирование**, чтобы находить и устранять новые узкие места.

#### Цели

Продолжим решать проблемы масштабирования, вытекающие из ограничений задачи:

* Если наша **база данных MySQL** начинает разрастаться сверх меры, можно хранить в ней только ограниченный по времени период данных, а остальное держать в хранилище данных (data warehouse) вроде Redshift
    * Хранилище данных вроде Redshift спокойно справляется с ограничением в 1 ТБ нового контента в месяц
* При 40 000 запросов на чтение в секунду в среднем трафик чтения популярного контента можно снять масштабированием **кэша в памяти**, что заодно помогает и с неравномерным распределением трафика, и со всплесками
    * **SQL read-репликам** может быть тяжело справляться с промахами кэша — вероятно, понадобятся дополнительные паттерны масштабирования SQL
* 400 операций записи в секунду в среднем (с заведомо более высокими пиками) может оказаться проблемой для единственного **master-slave SQL для записи**, что тоже указывает на необходимость дополнительных техник масштабирования

Паттерны масштабирования SQL включают:

* [Федерализацию](https://github.com/donnemartin/system-design-primer#federation)
* [Шардирование](https://github.com/donnemartin/system-design-primer#sharding)
* [Денормализацию](https://github.com/donnemartin/system-design-primer#denormalization)
* [Тюнинг SQL](https://github.com/donnemartin/system-design-primer#sql-tuning)

Чтобы дополнительно справиться с высокой нагрузкой на чтение и запись, стоит также рассмотреть перенос подходящих данных в [**базу данных NoSQL**](https://github.com/donnemartin/system-design-primer#nosql), например DynamoDB.

Можно и дальше разделять наши [**серверы приложений**](https://github.com/donnemartin/system-design-primer#application-layer), чтобы масштабировать их независимо. Пакетные процессы и вычисления, которые не обязательно выполнять в реальном времени, можно делать [**асинхронно**](https://github.com/donnemartin/system-design-primer#asynchronism) с помощью **очередей** и **воркеров**:

* Например, в фотосервисе загрузку фото и создание миниатюры можно разделить:
    * **Клиент** загружает фото
    * **Сервер приложений** кладёт задачу в **очередь**, например SQS
    * **Воркер-сервис** на EC2 или Lambda забирает задачу из **очереди** и:
        * Создаёт миниатюру
        * Обновляет **базу данных**
        * Сохраняет миниатюру в **объектном хранилище**
